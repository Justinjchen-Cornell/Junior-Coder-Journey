# 哈希表 · 教给别人版

## 给 8 岁孩子讲的版本

> 教室后面有一排储物柜，每个柜门上有号码。
> 每样东西放进去之前，先给它编个号（比如"书包"→3号柜），下次拿的时候直接奔 3 号柜——
> **不用翻遍所有柜子**。
> 这个"东西→柜号"的编号规则，就叫**哈希函数**；整排柜子叫**哈希表**。
> 但有个问题：两个东西编到同一个柜号怎么办？（比如"水杯"也算 3 号）→ 那就把 3 号柜**弄深一点**，里面挂一条链子，一个挨一个放。找的时候先奔 3 号柜，再在链子上找。

## 给大人讲的版本

- **哈希表 = 数组 + 哈希函数**：哈希函数把键映射为数组下标，理论上 O(1) 存取
- **冲突（collision）不可避免**：两个键映射到同一格 → 链式寻址（每格挂一条链）；链短则仍近似 O(1)
- **负载因子（load factor）= 键数/格子数**，超过 ~0.75 要**扩容**（翻倍 + 全部 rehash）——这是保持 O(1) 的工程底线
- **实测数据**（benchmark.py）：
  - 10 万键：哈希表 1000 次查找 3.85ms vs 线性查找 5310ms（**1379 倍**）
  - 坏哈希（按长度散列）：n=2000 就退化 4 倍；n=10 万时**直接卡死 2 分钟**（现场实测）
- **Python 的 dict 就是哈希表**——你天天在用，现在知道它为什么快了

## 代码逐行（solution.py 核心）

```python
def _hash(self, key):                 # ① FNV-1a 哈希函数（32 位）
    h = 2166136261
    for byte in str(key).encode():
        h ^= byte
        h = (h * 16777619) & 0xFFFFFFFF
    return h % self.size              # 映射到桶号

def put(self, key, value):
    idx = self._hash(key)
    bucket = self.buckets[idx]        # ② 找到桶（一条链）
    for i, (k, v) in enumerate(bucket):
        if k == key: bucket[i] = (key, value); return   # 已存在→覆盖
    bucket.append((key, value))       # ③ 新键挂链尾
    if self._load_factor() > 0.75: self._resize()       # ④ 扩容
```

## 经典用途（全是 O(1) 的胜利）

1. **查表**：价格表、通讯录、配置项
2. **去重**：投票防重、爬虫 URL 去重、访客统计
3. **缓存/记忆化**：函数结果缓存（动态规划的 memo 也是它）
4. **数据库索引**：底层就是 B+ 树和哈希索引

## 两个经典坑

1. **键必须可哈希**：Python 里 list/dict 不能当键（可变 → 哈希会变 → 找不回）；元组/字符串/数字可以
2. **哈希函数质量 = 生死线**：均匀散开 vs 全撞一桶（实测 4x ~ 卡死），工程上常用 FNV/SHA/Murmur；负载因子不扩容 → 链越来越长 → 悄悄退化成 O(n)

## 真实场景（它在哪工作）
- 🏠 生活：储物柜、手机通讯录"名字→号码"、字典查词
- 💻 互联网：Redis 缓存、数据库索引、CDN 内容寻址、爬虫 URL 去重、区块链哈希链、拼写检查
- 🧬 生物：DNA k-mer 索引（序列比对第一步）
- 💰 金融：行情快照 key-value、订单簿按价格档位、持仓查询 O(1)

## 局限性（它做不到什么）
- 无序：不支持范围查询（"3-5 元的水果"做不到）→ 该用树
- 冲突 + 负载因子：不扩容会悄悄退化成 O(n)（实测坏哈希卡死）
- 空间开销比数组大（桶+链表）；哈希函数质量决定命运
- 普通哈希 ≠ 加密哈希：存密码/签名要用 SHA-256 等

## 一句话总结

> **哈希表用"空间换时间"：把"找"变成"算"。** 它是本书第一个数据结构级的大杀器——也是 O(1) 神话的真相：前提是哈希函数够好、负载因子够低。
